## Capacity and ownership

No facilitator, participants, device QA person or independent reviewer has accepted an assignment in these records. By 30 October, the coordinator fills actual owner IDs and availability in each private roster and records only role assignments in the public handoff. Preparing invitations does not send them; no recruiting outreach is performed by this update.

The first round needs **24 registered candidate sessions involving 30 people** if participants are kept fresh across games: six Small Hours pairs (12 people), 12 Vivid people across two stories and six Bell people. Bell also has six reference runs within those same six paired comparisons. An optional neutral Iona cohort adds six more people/sessions. Preregistered failed attempts stay in the denominator; nonattendance remains visible and cannot be silently replaced with a success. Any rescheduling or exclusion follows the canonical protocol.

Reserve approximately **24 facilitator-hours plus device/reviewer time** for that first round as a staffing estimate, not a measured session duration: six 45-minute pair appointments, twelve 45-minute Vivid appointments and six 60-minute Bell comparisons, with roughly 20% administration buffer. Use the game protocol's actual run limits; appointments include setup, consent, recording and breaks. A changed-build release round can need the same capacity again. Parallel sessions need separate human facilitators and devices; agents cannot stand in for either.

## Publication dependencies and release records

On 28 October the dashboard was verified live from **main/root**, with six served files matching deployed main `1dd2330`. Earlier reads showed master and the source-update PUT returned 403; a later read and deployment established the new main state without proving that request succeeded. Read [PUBLISHING.md](../../PUBLISHING.md) for the full evidence. Verify the new official game URLs and deployment again at actual release; a live hub is not an approved game. Branch-protection enforcement is a separate dependency and must be observed, not inferred from workflow files.

The release path stays **game branch → master candidate → measured human evidence → independently reviewed promotion PR → main**. Do not merge whole game branches or the whole staging queue. The release registry is empty until a game qualifies. Keep current candidate numbers (Vivid 0.1.2; Bell 0.1.0) if their exact bytes qualify; any revised build gets a new unused version. Small Hours receives its first candidate version only when its prerequisite decision and checks support staging. No future version number or tag is claimed as published here.

For every actual release, record: source SHA; approved master SHA; inventory hash; human protocol/session references and reviewer; supported devices/limits; official version; `releases/<game>/<version>/build/index.html`; `notes.md`; actual GitHub release URL; deployment revision and verification time. Follow [the release policy](../../RELEASE-POLICY.md) for the exact registry schema and validator commands.

If a defect is found after launch, first reproduce it against the released hash and classify severity. Preserve the version, notes and evidence; prepare a corrected version through the same gate. If immediate mitigation is necessary, the maintainer may disable the affected entry point with a clear incident notice through reviewed hub maintenance while retaining the immutable package and version history. Do not silently replace shipped game bytes or roll back unrelated games.

## Checkpoints

Each game retains one source branch. Commit and push after the settled correction contract, after a verified playable change and after the final evidence handoff; verify the remote SHA each time. Update the main dashboard separately and back up before branch retirement. Store consent/contact/raw recordings outside Git; publish only necessary deidentified evidence after deliberate review. Use the [blank human-session template](../../../templates/game-demo/06A-HUMAN-SESSION.md) as a reusable aid; game-specific forms and canonical protocols govern these three studies.

The next restart checkpoint must name completed work, unfinished checks, exact branch/commits, dirty files, remote verification, backups, running services and restart commands. Codex allowance is unavailable; if the user reports below 5%, stop new work at a safe boundary, save that checkpoint and wait. This plan does not schedule an autonomous future launch or outreach.
