# MC-032 — Capture and recover my physical notebook page

Type: Story. Priority: P0 for the paper journey. Status: Proposed. Planning wave: Sprint 02 selected forecast. Owner roles: Client + Backend + QA; people unassigned. Allocation: 3 engineer-days and 1 QA day, subject to readiness review. Readiness: B1 ownership and B2 storage interfaces. Related parent cards: MC-002, MC-003, MC-004, MC-014, MC-015, MC-016, MC-017, MC-021.

As a paper-notebook writer, I want to capture a page into its matching digital notebook and recover its original, so that my writing stays identifiable and available across sessions.

## Acceptance criteria

- [ ] AC1. Camera permission denial and file import are usable on declared devices. Capture, preview, rotate, crop and retake operate on an actual photograph; none automatically asks the companion.
- [ ] AC2. Captures carry owner, notebook, physical page label, source ID and revision. Similar text on different pages remains distinct. Pairing/page codes never authorize reads. Another owner's source and thumbnail requests are rejected.
- [ ] AC3. Acknowledgement follows durable original bytes and metadata storage. Restart, interrupted upload, duplicate retry, quota failure and two-client handoff retain the original and truthful local/synced status.
- [ ] AC4. Retakes create revisions without silently replacing cited sources. Concurrent retakes expose a resolution path; cited versions remain accessible under retention rules.
- [ ] AC5. Processing sends only the selected derived image and permitted context. Location metadata is excluded from outbound images; logs omit page content and secrets. Export/import restores source bytes and association; deletion follows source/memory rules.
- [ ] AC6. Actual desktop upload, iOS camera/import and Android camera/import journeys include orientation, denied permission, restart and retry. Mobile compilation does not satisfy device acceptance.

## Implementation and evidence

Reuse notebook, ownership, document storage and journal modules after checking image support. Define original-asset retention, versioned crop transforms and idempotent capture operations. Keep original files independently of interpretation. Use MC-017 destination/revocation controls.

Evidence: navigation recording, image checksum before/after recovery, interrupted transfer, two-client revision trace, ownership tests and physical-device matrix. Parent cards require their full acceptance evidence. No capture implementation is claimed here.
