## User outcome

As a **AI user**, I want **working provider choices and an enforced model lock**, so that **cost and capability changes do not surprise me**.

## Why this work is needed

Preset/fixture integration is not proof of live model availability or price accuracy.

## Acceptance criteria

- [ ] **AC1.** Given two approved provider configurations, when each runs at least 100 real short turns across defined reply/vision scenarios, then model IDs, usage, errors and unsupported capabilities are recorded.
- [ ] **AC2.** Given strict model lock, when the model fails or lacks a capability, then the app reports it rather than silently substituting another model/provider.
- [ ] **AC3.** Given an unlocked budget-constrained route, when selecting a model, then capability, configured prices and country restrictions are checked; unknown prices are not treated as free.

## Implementation outline

1. Verify live capabilities and price configuration for selected connections.
2. Test rule routing, lock, timeouts and bounded retries.
3. Keep personal credentials isolated and endpoint-bound.

## Scope and readiness

Implement this bounded outcome; preserve the accepted ink interaction and existing functionality.

**Readiness:** Two valid providers, approved handling terms and a spending allowance are required.

## Required review artifacts

- Two live provider run sets
- Lock/failure traces
- Capability/price review

## Definition of done and evidence

Acceptance criteria pass on the candidate revision; changed behavior has meaningful tests and relevant UI checks; critical privacy/data-loss defects are closed. Record the source/deployment, test environment and limitations. A fixture does not count as a live provider test, and a mobile bundle does not count as physical-device evidence.
