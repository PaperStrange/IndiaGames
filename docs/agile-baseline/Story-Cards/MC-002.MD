## User outcome

As a **notebook owner**, I want **verified sessions and isolated data**, so that **other users cannot access my notes or companion history**.

## Why this work is needed

Private edge identity and owner fallback are unsuitable for public/native sessions.

## Acceptance criteria

- [ ] **AC1.** Given users A and B, when A guesses B’s note, document, memory, export or tool-context identifier, then the request is rejected without content leakage.
- [ ] **AC2.** Given an expired or revoked session, when a client reads or writes, then access is denied and unsynced edits remain available for recovery after reauthentication.
- [ ] **AC3.** Given browser and native test clients, when sessions are created, then identity is server verified; client-supplied owner headers and the private-owner fallback cannot grant access.

## Implementation outline

1. Select session approach under ADR from MC-001.
2. Enforce ownership on API and object access; implement revocation.
3. Exercise two-user and expired-session cases.

## Scope and readiness

Implement this bounded outcome; preserve the accepted ink interaction and existing functionality.

**Readiness:** Session approach, test identities and server configuration must be available.

## Required review artifacts

- Two-user isolation results
- Session expiry/revocation evidence
- Web/native contract review
