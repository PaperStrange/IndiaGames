## User outcome

As a **person writing offline**, I want **my edits durably saved on this device**, so that **a reload does not silently erase acknowledged work**.

## Why this work is needed

Version-checked server snapshots do not provide a durable local operation queue.

## Acceptance criteria

- [ ] **AC1.** Given a local edit, when durable persistence succeeds, then the UI may show saved on device; it must not claim synced without a server acknowledgment.
- [ ] **AC2.** Given an acknowledged local edit, when the application is terminated and reopened on the same intact device, then the edit and pending operation are restored exactly once.
- [ ] **AC3.** Given quota or persistence failure, when saving fails, then the UI shows the failure and preserves a recoverable in-memory copy without claiming durability.

## Implementation outline

1. Implement durable operation storage with IDs and source revisions.
2. Hydrate pending edits and handle storage failures.
3. Add restart/failure scenarios to the shared fault suite.

## Scope and readiness

Single-device durability first; loss of the only unsynced device is explicitly outside recoverability.

**Readiness:** None identified beyond dependencies; refine before commitment.
