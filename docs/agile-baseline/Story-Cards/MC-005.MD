## User outcome

As a **person connecting AI**, I want **a real response with identifiable provider and usage**, so that **I know the connection works and can inspect its cost**.

## Why this work is needed

Adapters have fixture coverage, but live provider latency and billing are unverified.

## Acceptance criteria

- [ ] **AC1.** Given a valid selected connection, when a synthetic short prompt and a permitted handwriting sample are sent, then genuine reply/vision results, actual model and available usage are recorded.
- [ ] **AC2.** Given a trace, when it is inspected, then input end, request, first delta and visible reply timestamps are separate; missing usage is marked unknown rather than zero.
- [ ] **AC3.** Given invalid credentials, unsupported vision or timeout, when a request fails, then input is recoverable and no sample is presented as a real response.

## Implementation outline

1. Securely configure one provider without putting keys in tickets or logs.
2. Add minimal route/timestamp/usage trace fields.
3. Run a small real smoke set and document errors.

## Scope and readiness

First live smoke slice only. Two-provider 100-turn gates and reconciled metrics remain MC-011/012.

**Readiness:** BLOCKED until a valid provider connection and spending allowance are available.

## Required review artifacts

- Sanitized live-run records
- One actual handwriting interpretation
- Failure states and cost assumptions

## Definition of done and evidence

Acceptance criteria pass on the candidate revision; changed behavior has meaningful tests and relevant UI checks; critical privacy/data-loss defects are closed. Record the source/deployment, test environment and limitations. A fixture does not count as a live provider test, and a mobile bundle does not count as physical-device evidence. See [the shared checklist](../03-READY-DONE-AND-QA.MD).
