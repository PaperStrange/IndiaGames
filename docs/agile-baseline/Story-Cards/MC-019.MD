## User outcome

As a **user seeing a harmful or wrong reply**, I want **an in-app report and correction path**, so that **the problem can be fixed without losing my writing**.

## Why this work is needed

No owned end-to-end reporting/incident operation is established.

## Acceptance criteria

- [ ] **AC1.** Given a problematic reply, when I report it in the app, then the report reaches an owned queue with minimal context and acknowledgment.
- [ ] **AC2.** Given a related bad learned memory, when corrected or forgotten, then its status is visible and the relevant invalidation path runs.
- [ ] **AC3.** Given a simulated severe incident, when triaged, then an accountable owner can contain, investigate, communicate and verify recovery using the playbook.

## Implementation outline

1. Build report UI and restricted queue.
2. Assign severity/ownership and rollback procedures.
3. Run one incident drill.

## Scope and readiness
