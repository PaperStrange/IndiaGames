## User outcome

As a **international user**, I want **honest availability and appropriate local handling**, so that **the app does not silently send data through an unapproved route**.

## Why this work is needed

Global requirements are planned; launch markets and eligibility enforcement are not established.

## Acceptance criteria

- [ ] **AC1.** Given an unapproved country/provider/feature combination, when requested, then server policy denies it and no silent alternative-region fallback occurs.
- [ ] **AC2.** Given an admitted market, when reviewed, then language, notices, provider terms, payments and operational ownership have evidence and sign-off.
- [ ] **AC3.** Given a routing-policy change, when deployed, then affected users receive an accurate supported state and rollback is available.

## Implementation outline

1. Resolve initial market and eligibility policy; separate locale from legal jurisdiction.
2. Enforce policy server-side and test failure states.
3. Document reviewed market records without claiming worldwide compliance.

## Scope and readiness

Implement this bounded outcome; preserve the accepted ink interaction and existing functionality.

**Readiness:** Initial market, handling policy and qualified review required.

## Required review artifacts

- Eligibility matrix
- Server denial cases
- Selected-market readiness record

## Definition of done and evidence

Acceptance criteria pass on the candidate revision; changed behavior has meaningful tests and relevant UI checks; critical privacy/data-loss defects are closed. Record the source/deployment, test environment and limitations. A fixture does not count as a live provider test, and a mobile bundle does not count as physical-device evidence. See [the shared checklist](../03-READY-DONE-AND-QA.MD).
